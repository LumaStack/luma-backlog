# The injected CLAUDE block should say that foreman wires bundles up

## The idea

**The block `luma-foreman apply` injects into `CLAUDE.md` should make the model
fully understand that luma wires up bundles** --- and that **it should not try to
edit `CLAUDE.md` in order to get them loaded.**

This is what it injects today:

```
<!-- luma:begin --- generated by `luma-foreman apply`. Edits between these markers are lost. -->

## Knowledge this project has adopted

**Read `.luma/bundles/INDEX.md` now.** It lists what this project knows, what
each part is for, and what brings it into play. Nothing below repeats it.

@.luma/bundles/INDEX.md

Generated by `luma-foreman apply`. Edits between the markers are lost;
everything outside them is yours.

<!-- luma:end -->
```

---

*Everything above is the maintainer\'s, with wording improved and intent
unchanged. Everything below was added by the agent while capturing it.*

## In the capturing agent\'s own words

**The block says what is adopted and how to read it. It says nothing about who
does the wiring.** So an agent that wants a rule to be in play reaches for the
file in front of it, because nothing tells it that file is an output.

## Ideas and concerns from the capturing agent

### This is written from the failure, an hour old

**An agent --- this one --- added a rule to a bundle policy, judged that it would
not reach a plain conversational turn, and hand-wrote a copy into `CLAUDE.md`
outside the markers to make it fire.** The maintainer stopped it and it was
reverted.

**Nothing in the injected block would have prevented that.** *Edits between the
markers are lost* is a warning about **where** to edit, and it reads as
permission for everywhere else. What was missing is that **a rule does not belong
in this file at all** --- it belongs in a bundle, and foreman carries it here.

### The version in the always-loaded index is stale right now

**`INDEX.md` says `local/backlog` 0.27.0. The bundle is at 0.36.0.** Nine
versions, all written today, in the one file that is always in context.

**That is the same failure from the other direction.** The block is a generated
view of the bundles and nothing runs the generator, so the file every agent
reads first is quietly describing a corpus that has moved. **An agent trusting
the index would be nine versions behind and have no way to tell.**

Worth saying out loud: **the index carrying versions is what makes this
checkable**, and it is the reason the staleness was noticeable at all.

### What the block might say

Not proposed as wording, only as the content it is missing:

- **Foreman installs procedures into the harness as skills** --- `INDEX.md`
  already says this in passing and the injected block does not.
- **A rule belongs in a bundle.** If something should be in play, that is a
  bundle change followed by `apply`, never an edit here.
- **This block is generated and so is the index it points at.** Their contents
  are downstream of `.luma/bundles/`, and editing either is editing a rendering.
- **How to tell whether it is current** --- the versions here should match the
  bundles, and if they do not, `apply` has not run.

### Where it belongs and the shape of the fix

**`luma-foreman`, which is a third project** --- not luma-backlog, not
luma-catalog. **Fourth idea in a row captured into the wrong corpus**, and more
evidence for
[[work-items/WORK-0090-session-save-and-session-end-and-moving-a-record-to-the-project-it-belongs-in]].

**And it interacts with**
[[work-items/WORK-0092-a-policy-marked-eager-does-not-reach-a-plain-turn]]:
telling an agent not to edit `CLAUDE.md` closes the wrong door if the reason it
reached for it --- a policy that never loads --- is left open. **The two are one
question with two halves**: what an agent must not do, and what it should do
instead.
